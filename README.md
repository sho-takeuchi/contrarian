# 銘柄の記録と分析（データを蓄積して分析する）

日本株・REITのスクリーニング結果と、その後の株価・分析を自分のPCに蓄積し、チャットで理由や根拠を確認できるアプリです。

月足の第1段階と週足の第2段階を両方通過した銘柄を毎日自動で記録します。通過しなくなったときに、開始時から株価が上昇したか、下落したかを分類し、終了理由と関連する開示・ニュースを根拠に分析結果を保存します。

**初回設定後は、自動で記録・分析が進みます。知りたいことがあれば、チャットで質問できます。** 銘柄の登録、株価更新、資料収集、分析の実行を日々操作する必要はありません。

例えば「なぜ上昇して通過終了したのか」「なぜ下落して通過終了したのか」を質問すると、保存済みの株価・判定条件・自動分析・根拠資料を確認できます。

## 対象と判定

対象は上場8年以上の日本株・REITです。必要な価格・上場日がそろわない場合は判定不能として記録します。

| 段階 | 確認する条件 |
|---|---|
| 第1段階：月足 | 長期安値圏の許容上限内にあり、直近3確定月の安値を維持し、確定月の終値が3か月平均を上回る |
| 第2段階：週足 | 確定週の終値が5週平均を上回り、5週平均も前週より上向く |

**この2段階を両方通過した銘柄が、自動記録・分析の対象です。** 詳細な式や欠損の扱いは [判定仕様](docs/screening.md#7-判定仕様) を参照してください。従来の日足による第3段階の判定も、手動CLIで利用できます。

## チャートのイメージ

同じ架空銘柄が第1〜第3段階の条件をすべて満たす例です。月足の長期安値圏・反発、週足の上向き、日足の短期調整を並べています。実在の銘柄や株価ではありません。

## 何を蓄積するのか

「どの銘柄が条件を満たしたか」に加え、「その後どうなったか」を通過期間ごとに残します。

| 記録する内容 | 後から確認できること |
|---|---|
| 通過開始日と、その時点の月足・週足の条件値 | どのような状態で通過を始めたか |
| 日々の判定と株価 | 通過が続いているか、開始日からどう動いたか |
| 通過終了日・終了時騰落率・不成立になった条件 | 上昇して終了したか、下落して終了したか、どの条件を外れたか |
| 企業開示・決算情報・ニュースと取得状況 | 値動きを考える際に参照できる情報と、取得できなかった情報 |
| 個別の分析・全体の比較・変更前の分析 | 確認できた根拠と、蓄積によって見えてきた傾向 |

一度第2段階まで通過した銘柄は、通過終了後も株価の取得を続けます。

## 毎日の流れ

```text
全銘柄を月足・週足で判定
  → 第2段階まで通過した銘柄と条件をDBへ保存
  → 過去に通過した銘柄も含めて株価を更新
  → 通過の継続・終了・再通過を記録
  → 終了時の上昇・下落を分類
  → 開示・ニュースを収集し、資料を検索して分析
  → 個別分析と全体の傾向をDBへ保存
```

定期処理は15分間隔で確認し、**営業日の日本時間18時以降、当日の株価データの公開を確認して判定**します。完了済みの処理は重複登録せず、未完了の処理を再試行します。

PCを起動・ログインし、DockerとOllamaを稼働させて利用します。PC停止中の株価は取得可能な範囲で補完します。実行しなかった日のスクリーニング結果は作らず、未観測として記録します。

利用者は、蓄積された結果を一覧で見たり、チャットで終了理由や分析の根拠を質問したりできます。チャットで質問していない間も、自動記録・分析は進みます。

## 画面の使い方

起動後は [http://127.0.0.1:8501/](http://127.0.0.1:8501/) を開きます。画面は1分ごとに保存済みの結果を読み直します。

画面上部には **「チャットで質問する」** があります。その下の「自動分析のまとめ」と更新状態で、蓄積状況を確認できます。

銘柄の一覧は、次の4つの表示を切り替えて確認します。

| 表示 | 確認する内容 |
|---|---|
| **通過中** | 第2段階まで通過している銘柄、通過開始日、最新株価、開始日比騰落率 |
| **上昇して通過終了** | 開始日より株価が上昇した状態で条件を外れた記録と、その分析 |
| **下落して通過終了** | 開始日より株価が下落した状態で条件を外れた記録と、その分析 |
| **変化なし・要確認** | 騰落率0％、判定不能、観測の途切れ、必要な株価の不足など |

各表示の **「銘柄の記録を見る」** で銘柄・通過期間を選ぶと、株価グラフ、日々の判定、通過終了理由、自動分析、根拠資料を確認できます。「判定履歴・資料の取得状況」を開くと、資料ごとの取得済み・該当情報なし・再試行待ちも分かります。

## チャットで理由と根拠を確認する

**「チャットで質問する」** を開き、入力欄に質問を書いて送信します。

| 確認したいこと | 質問例 |
|---|---|
| 上昇して通過終了した理由 | 「上昇して通過終了した銘柄は、なぜ終了した？」 |
| 下落して通過終了した理由 | 「下落して通過終了した理由と根拠を教えて」 |
| 特定銘柄の記録 | 「2499の通過終了理由は？」「2499の記録は？」 |
| 直前の回答の根拠 | 「その根拠を詳しく教えて」 |
| 上昇・下落の全体傾向 | 「上昇と下落の共通傾向は？」 |

銘柄は4桁・5桁のコード、または記録されている銘柄名で指定します。対象が多い場合は新しい順に10件ずつ表示し、「残りを教えて」で続き、「全体」を含む質問で銘柄指定を外した全体の記録を確認できます。

回答では、次の内容を分けて示します。

1. **上昇・下落の分類の根拠**：通過開始日と終了日、調整後終値、終了時騰落率。
2. **条件を外れた理由**：満たさなくなった月足・週足の条件と、判定に使った数値。
3. **値動きに関連する資料・自動分析**：保存済みの分析、検証できた引用、根拠資料のURL、資料の取得状況。

実行IDと分析の保存日時も示します。終了例がまだない場合、必要な株価が欠けている場合、自動分析が準備中の場合は、その状態を回答します。根拠が不足する場合は「要因を特定できない」と示し、条件不成立をそのまま株価変動の原因とは扱いません。

チャットは保存済みの結果を読み出して回答します。質問によって株価取得・資料収集・自動分析の定期処理を開始することはありません。Ollamaが停止中でも、既に保存された分析は確認できます。会話はブラウザのセッション内に保持し、DBへは保存しません。

画面には分析開始・手動更新・資料登録・追跡停止の操作はありません。運用保守はCLIで行います。

## 通過期間と上昇・下落の数え方

初めて通過を観測した日を開始日とし、連日の通過を1つの期間にまとめます。月足・週足のどちらかが明確に不通過になれば終了し、その後の再通過は別の期間として保存します。同日の再実行は、その日の最新の正常な全銘柄実行を代表として採用します。

終了時の分類には、分割・併合の調整基準をそろえた終値を使います。

```text
終了時騰落率（％）=（通過終了日の終値 ÷ 通過開始日の終値 − 1）× 100
```

例えば開始時100円、終了時115円なら「上昇して通過終了（+15％）」、終了時90円なら「下落して通過終了（−10％）」です。上昇して月足の許容上限を超えた場合も、終了記録に含まれます。

- 終了後の値動きによって、この上昇・下落の分類を変えることはありません。価格訂正による再評価は、変更前の記録を残して行います。
- 未実行・判定不能・株価欠損は不通過や0％に置き換えません。連続性を確認できない期間は「要確認」とし、上昇・下落の全体比較から除外します。
- 配当と売買費用は騰落率に含めません。
- 同じ銘柄の再通過は別の記録になるため、通過期間の件数とユニーク銘柄数を分けて集計します。

## 自動分析で分かること

**「通過しなくなった理由」** は、月足・週足の判定値と条件から確定します。**「株価が動いた要因」** は、その期間までに公表された開示・決算情報・ニュースを参照し、関連が考えられる材料として保存します。

本文や発表日時を確認できない記事は、見出しだけで値動きの原因と断定しません。通過終了後に発表された情報を、それ以前の値動きの原因として扱うこともありません。根拠が足りない場合は、**「要因を特定できない」** という結論を保存します。

資料は通過開始の直前30日から取得可能な範囲で集め、日々追加します。通過終了後7日間は遅れて取得される情報も確認し、根拠が増えた場合は分析を改版します。情報源の収集範囲・接続・利用制限による不足も記録します。

全体の分析では、同じ判定ルールの中で上昇終了群と下落終了群の開始条件・通過期間・終了理由・資料の分類を比較します。**上昇・下落それぞれ10銘柄未満の間は「蓄積不足」** と表示します。個別の記録は初日から蓄積します。

分析が示すのは観測された関連です。因果関係の確定や将来の株価予測、売買の自動実行は行いません。

## LLMのモデルはPC内で実行

**自動分析用LLMと埋め込みモデルをOllamaでPCにダウンロードし、ローカルで実行します。** 収集した資料は同じPCのPostgreSQLに保存し、pgvectorで関連箇所を検索するRAG構成です。チャットは、この仕組みで蓄積された分析と根拠資料を参照して回答します。

| 構成 | 役割 |
|---|---|
| PostgreSQL | 判定履歴、通過期間、株価、資料、分析とその変更履歴の保存 |
| pgvector | 資料の埋め込みと関連箇所の検索 |
| Ollama：`llama3.1:8b` | 関連資料から分析の根拠となる記述を抽出 |
| Ollama：`embeddinggemma:300m` | 資料と検索文の埋め込み生成 |
| Python／SQL | 合否、価格調整、騰落率、比較集計、LLMの引用検証、チャット用の記録の読み出し |
| Streamlit | 結果の一覧・銘柄詳細と、理由や根拠を質問するチャット |
| SQLite | スクリーニング用の株価取得キャッシュ |

モデルは設定で変更できます。外部のクラウドLLMへの送信を前提とせず、株価取得・資料収集・初回のモデル取得にはインターネット接続を使用します。Ollamaが停止していても判定・株価の保存を進め、資料の索引作成とLLMによる分析は後から再試行します。

### 利用する情報源

| 情報源 | 主な用途 | 準備するもの |
|---|---|---|
| J-Quants | 株価・出来高、契約範囲内の決算・業績予想情報 | API v2キーと、必要な過去データ・一括取得を利用できる契約。本実装はStandardプランを前提 |
| JPXの上場日CSV | 月足判定に使う上場日の確認 | 公式CSVを取得して取り込み |
| EDINET API v2 | 有価証券報告書・半期報告書・臨時報告書など | 利用登録とAPIキー |
| GDELT DOC API | 会社に関連するニュースの検索 | APIキーの設定は不要 |

EDINETキーが未設定なら準備待ちとして表示し、利用可能な情報源で処理を続けます。EDINET・GDELTがすべての開示・ニュースを網羅することは前提にしていません。

## 導入の流れ

Python 3.11以上、Docker Compose、Ollamaを使用します。macOS・Windowsのユーザー用スケジューラで定期実行できます。

1. このリポジトリを取得し、仮想環境にスクリーニング用・分析用の依存をインストールする。
2. `.env.example` を参考に `.env` を作り、DB接続先、J-Quantsキー、EDINETキーを設定する。
3. JPXの上場日CSVを取り込む。
4. PostgreSQLを起動してDBを初期化し、Ollamaの2つのモデルを取得する。
5. 接続を診断し、既存の結果があれば取り込む。
6. 定期処理を登録し、ダッシュボードを起動する。

**OS別のコピー可能なコマンド、設定項目、初回実行の説明は [自動記録・分析の導入と運用](docs/analysis.md#初回設定保守) にまとめています。** 既に稼働中の環境では初期設定をやり直す必要はありません。

初回は過去10年分の株価取得とモデルのダウンロードに時間・保存容量が必要です。画面を開くだけではスクリーニングを開始しません。定期実行の登録と、DB・Ollama・画面の起動はそれぞれ確認してください。

## データの保存先

| 保存先 | 内容 |
|---|---|
| PostgreSQLの永続ボリューム | 判定結果、通過期間、共通の株価、資料・索引、分析と改版履歴 |
| `outputs/<実行ID>/` | 元となる判定CSVと実行記録 |
| `data/` | 株価キャッシュ、入力スナップショット、自動処理の状態 |
| `inputs/` | 上場日CSVと取得元の記録 |
| `logs/` | 定期実行などの運用ログ |

通常の自動処理は第2段階まで実行するため、`outputs/<実行ID>/candidates.csv` が月足・週足を両方通過した銘柄です。`stage1_candidates.csv` は月足の通過銘柄、`all_results.csv` は不通過・判定不能も含む全件結果、`run.json` は判定日・ルール・件数・ハッシュなどの実行記録です。

手動で第3段階まで実行した場合は、`stage2_candidates.csv` が月足・週足の通過銘柄、`candidates.csv` が日足も通過した最終候補になります。**`candidates.csv` の意味は実行段階によって変わるため、パスと `run.json` の段階を合わせて確認してください。**

認証情報、実データ、資料、ログ、バックアップはGit管理から除外しています。更新や移行の前にはDBとローカルファイルをバックアップしてください。[バックアップ・復元と障害対応](docs/analysis.md#バックアップ復元と障害対応) に手順があります。
